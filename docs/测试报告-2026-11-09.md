# strm-scraper 整体性与集成测试报告

- 测试对象：`strm-scraper` 工作区（基线提交 `bbdb855` + 上一轮 5 项未提交修复）
- 测试日期：2026-11-09
- 测试性质：只读诊断，**未修改任何产品代码**
- 本地环境：`127.0.0.1:6700`（主集成）、`127.0.0.1:6702`（鉴权）、`127.0.0.1:6720`（慢速源，接受连接但不应答）
- 线上环境对照：`100.66.1.1:6666` 仍为已发布的 `bbdb855`，本轮结论对线上同样适用，但**不含**未提交修复

## 1. 结论摘要

1. **主干功能是通的。** 离线 239 项断言 0 失败，在线 16 个套件（约 475 项断言 + 4 个零失败巡检）全部通过；扫描 → 派发 → 探测 → 抓帧 → 出图 → NFO → 通知 Emby/Jellyfin → 定时/实时触发这条主链在夹具库上无回归。
2. **发现 2 个 P1、5 个 P2、2 个 P3、3 个 P4。** 没有发现数据损坏、任务丢失、越权访问这类阻断级问题；两个 P1 都属于「用户以为能做、实际做不到」的功能缺口。
3. 最该先修的三件事：
   - **单条「立即执行」无法暂停/取消**（按钮被禁用、接口回 409），慢源下只能干等；
   - **`/api/settings` 校验失败仍会把前半段配置写进内存**，接口报错但配置已生效；
   - **限流信号用裸数字匹配**，文件名里带 `429` 会触发全进程 5 分钟退避。
4. 上一轮修复里 `links` 的裸数字误判已改用语义正则（`_STATUS_RE`），但 `throttle` / `probe` 两处同类代码**没有跟上**——这是本轮最典型的「修了一处、漏了两处」。
5. 建议：P1 与限流误判进下个补丁；探测可中断、全量扫描范围、闸门降级复位进再下一个；其余按迭代清理。

## 4. 问题清单（按严重程度）

### P1-1 单条「立即执行」无法暂停 / 取消，按钮同时被禁用

**位置**
- `scraper/web.py:1412` — `process(cfg, build_target(...), frame_at=..., force=force)` **没有传 `abort`**
- `scraper/web.py:1361-1405` — `single_active` 是一份独立的在跑登记表，与 `Runner` 无关
- `scraper/web.py:1260-1279` — `pause` / `cancel` 只询问 `runner.pause()` / `runner.cancel()`
- `scraper/worker.py:223-225` — `busy()` 只看 Runner 自己的状态机
- `static/index.html:2506` — 按钮禁用条件只看任务 `state`

**触发条件**
在「文件管理」里对单个文件点「刮削」（走 `_spawn_single`），此时没有批量任务在跑；随后点「暂停」或「取消」。

**影响**
- `/api/task/pause`、`/api/task/cancel` 直接返回 409「当前没有可暂停/取消的任务」；
- 前端 `btnPause` / `btnCancel` 同时是 disabled，用户**没有任何入口**中止；
- 用慢源（只 accept 不应答）实测：单条任务卡满 7.2s（探测超时 8s 的等满）才结束，期间只能刷新页面干等；
- 如果这条源是「半死」状态又开了多帧采样，阻塞时间会成倍放大；`single_active` 只在 `finally` 里清理，线程若被强杀会留下脏登记，后续同名文件点「刮削」会被静默跳过（`web.py:1370`）。

**修复建议**
1. `_spawn_single` 为每个 path 建一个 `threading.Event`（`dict[str, Event]`），传给 `process(..., abort=ev)`；
2. `task_pause` / `task_cancel` 先判断 `single_active`：有则 set 所有 event 并返回 200，文案区分「已暂停单条任务」；
3. `busy()` 改为 `self.state != "idle" or bool(single_active)`（或提供一个统一的 `web.busy()`），消除两套「忙」判断；
4. 前端按钮条件加上 `snapshot.single.count > 0`（该字段 `web.py:869` 已经在返回）。

### P1-2 `/api/settings` 校验失败仍会改写内存配置（非原子）

**位置**
- `scraper/web.py:2690-2694` — docstring 明确承诺「先逐项校验，全部通过才改内存」「任何一项不合法都整单拒绝」
- `scraper/web.py:2715` — 实际在这里就把 `cfg.scan.roots` 写进去了
- `scraper/web.py:2790` — servers 校验抛 `HTTPException(400)`
- `scraper/web.py:2835` — `links.configure(cfg, store)` 在异常路径上根本执行不到

**触发条件**
一个请求里既有合法字段又有非法字段，例如：

```json
{"scan": {"roots": ["/alt-library"]}, "servers": [{"enabled": true, "url": ""}]}
```

**影响**
- 接口返回 400，前端提示「保存失败」，但 `/api/config` 已经返回新的 `roots`，后端下一轮扫描立刻按新目录走（实测复现：400 之后 roots 已变成 `alt-library`）；
- 更隐蔽的是组件不同步：`cfg.links` 可能已被改动，而闸门内的 `links.SETTINGS` 还是旧值（因为 `configure()` 没执行），`pool` 缓存与调度器也没重配 —— 运行态与配置对象分裂，直到下一次成功保存或重启；
- 用户视角是「我明明保存失败了，怎么库变了」，排查成本很高。

**修复建议**
改成两段式，不要在 `cfg` 上边校验边赋值：

```python
draft = copy.deepcopy(cfg)          # 或 dataclasses.replace 逐层构造
...                                  # 所有校验/赋值只作用于 draft
cfg = draft                          # 全部通过后整体替换
links.configure(cfg, store); pool.reset_cache(); sched.reconfigure()
cfg.save()
```

不想深拷贝就退一步：入口存 `snapshot = copy.deepcopy(cfg)`，`except HTTPException` 分支里 `cfg.__dict__.update(snapshot.__dict__)` 后重新抛出。并补一条在线断言：400 之后 `/api/config` 必须与请求前一致。

### P2-1 探测阶段无法中断，暂停/取消要等满一个探测超时

**位置**
`scraper/probe.py:174-181` —— `abort` 只用于 `links.lease()` 领票阶段；真正执行是 `subprocess.run(cmd, timeout=timeout + 10)`，**执行期间完全不看 `abort`**。

**触发条件**
任一 `process()` 正处于 ffprobe 阶段（网络源慢、不应答、半开连接）时点「暂停」或「取消」。

**影响**
- 批量任务实测：`pause` 后 `active` 从 2 → 1 后**卡 7.4s** 才清空（`probe_timeout=8`）；
- `probe_timeout` 可配到 600，最坏情况要 610s 才响应暂停，这段时间 `/api/status` 仍显示 running，用户会以为按钮失灵；
- 与 `frames.py` 的实现不一致：那边用 `Popen` + 100ms 轮询 `abort`，能真正即时杀掉 ffmpeg。

**修复建议**
把 `probe()` 改成可中断执行，照抄 `frames._run_ffmpeg` 的循环：

```python
proc = subprocess.Popen(cmd, stdout=PIPE, stderr=PIPE, creationflags=creation)
while proc.poll() is None:
    if abort is not None and abort.is_set():
        proc.kill(); proc.wait()
        raise links.LinkAborted("探测阶段任务已暂停")
    time.sleep(0.1)
```

注意不要 `import frames`（`probe ← frames` 已存在依赖，反向会成环）；`CaptureAborted` 建议提到公共模块，或直接复用 `links.LinkAborted`（`_single_worker` / `_work` 都已捕获它）。

### P2-2 全量扫描会复活「已不在扫描根内」的历史记录

**位置**
`scraper/worker.py:488` —— `reset = self.store.reset(("ok", "skipped", "failed"))` 是**整表**操作，不按 roots / `all_paths` 过滤。对比增量分支（`:494-518`）全程用 `self._scope()` 和 `all_paths` 限定范围。

**触发条件**
用户把某个库从 `scan.roots` 移除（换盘、改名、临时下线），旧记录仍留在 `items` 表；之后跑一次「全量扫描」。

**影响**
- 旧库条目被重置成 pending 重新入队 → 请求不存在的路径、计入失败、`attempts` 累加；
- 实测：`已删除的旧库/ghost.strm` 从 `ok` 变成 `failed`，`attempts=2`；
- 列表里长期挂一批 `failed` 幽灵项，污染统计、干扰「重试失败」操作，用户会以为刮削本身有问题。

**修复建议**
- 全量 reset 也限定在当前扫描结果内：给 `state.reset()` 加 `paths=` 参数（分批 `WHERE path IN (...)`），或直接用已有的 `store.reset_many(all_paths)`；
- 不在 roots 下的记录保留原状态、或标记为 `orphan`，在 UI 提供显式「清理不在库内的记录」，**不要自动重跑**。

### P2-3 闸门降级状态跨任务残留，`RequestGate.reset()` 是死代码

**位置**
- `scraper/links.py:401-407` 定义了 `reset()`，注释写着「任务开始时清掉降级状态」，但**全仓没有任何调用点**（`grep GATE.reset` 为空）；
- `scraper/worker.py:253` 只调了 `throttle.GUARD.reset()`。

**触发条件**
任一次 403 / 429 / 5xx → `_observe()` 置 `_adaptive = 1`、`_degrade_until = now + cooldown`；任务结束后这两个状态都不会清。

**影响（实测，`max_inflight=4` / `recover_every=8` / `cooldown=60s`）**

| 场景 | 结果 |
| --- | --- |
| 一次 403 之后 | `active_limit = 1`，`adaptive = 1` |
| 紧接着开下一轮任务 | `GUARD.remaining = 0`（已复位）**但 `GATE.active_limit` 仍为 1** |
| 冷却期内连续成功 20 次 | 仍是 1 路（`_observe` 要求 `now >= _degrade_until` 才允许回升） |
| 冷却期满后 | 每 8 次成功 +1 档，12 次成功 → 2 路，80 次 → 回到 4 路 |

两套降级机制行为不对称：`GUARD` 每轮清、`GATE` 从不清。撞过一次 403 后，如果后续都是小批量任务（只勾 3 个文件），单轮永远凑不满 8 次成功，跨轮累计也很慢 —— 表现为「撞一次墙之后一直很慢」，而 `/api/links` 里看不到 `adaptive` 值，排查时没有抓手。

**修复建议**
二选一，并写进 `docs/115-links.md`：

- **(a) 对齐复位**：`Runner.start()` 与 `_spawn_single` 入口调 `links.GATE.reset()`，与 `GUARD.reset()` 保持一致。我倾向这个 —— 一次 403 往往是瞬时的，任务边界是最自然的复位点。
- **(b) 保留跨任务降级 + 空闲衰减**：`_limit()` 里若 `now >= _degrade_until` 且距上次请求超过 `2 × cooldown`，则 `_adaptive = 0`。

无论选哪个，都把 `adaptive` / `degrade_until` 剩余秒数加进 `/api/links` 的 `gate` 字段。

### P2-4 登录限流以 `X-Forwarded-For` 为准，可被绕过

**位置**
- `scraper/web.py:85-89` — `_client_ip()` 无条件取 XFF 第一段；
- `scraper/auth.py:247-273` — `LoginThrottle` 按这个 key 计数（默认 5 次 / 300s）。

**触发条件**
服务直接暴露（没有反向代理），攻击者每次登录请求换一个 XFF 值。

**影响**
- 实测：带不同 XFF 连续失败 10 次仍是 401，**不触发锁定**；不带 XFF 时第 6 次起 429 —— 说明限流本身有效，但 key 可伪造；
- 反向也可用来「栽赃」：伪造受害者 IP 打满额度，把正常用户锁在门外；
- 注意这是「配置默认值」问题而非实现错误：部署在反向代理后时，XFF 是代理写的，行为正确。

**修复建议**
- 增加 `auth.trust_proxy`（默认 `false`）：`false` 时只用 `request.client.host`；`true` 时取 XFF 的**最后一跳**（`split(",")[-1].strip()`，即代理追加的那段），而不是第一段；
- 另加一道与 IP 无关的全站熔断（例如 20 次失败 / 5 分钟），避免换 IP 绕过；
- 文档里补一句「反向代理部署才需要开 `trust_proxy`」。

### P2-5 限流信号用裸数字子串匹配，URL / 文件名里的数字会被误判

**位置**
- `scraper/throttle.py:32-59` — `_PATTERNS` 含裸 `"403" / "429" / "503" / "504"`，对整段 stderr 做 `in` 判断；
- `scraper/probe.py:127-148` — `_classify_error()` 同样是 `"429" in text` 这类判断；
- 对照：`scraper/links.py:63-66` 已经用 `_STATUS_RE` 修过同类问题（只在「返回 / returned / error / status 404」这类语义里才认），**另外两处没跟上**。

**触发条件**
源地址或文件名里带这几个数字，例如 `http://host/movie.429.mp4` 实际返回 404。

**影响**
实测 `"http://host/movie.429.mp4: Server returned 404 Not Found"`：

- `throttle.detect()` 返回 `"429"` → 错误文案变成「地址返回 429…已自动退避」，把「文件不存在」误报成「被限流」，排查方向直接跑偏；
- 触发全局 `GUARD` 退避：5s → 15s → 45s → 135s → 300s。一批这类文件串行过一遍，**全进程网络出口停摆 5 分钟**；
- `RequestGate._observe()` 也会把并发降到 1 并进入冷却 —— 一个文件名就能让整个批量任务变慢。

**修复建议**
- 把 `links._STATUS_RE` 提到公共位置（如 `throttle.STATUS_RE`），`throttle.detect` / `probe._classify_error` 共用；
- 匹配前先把 stderr 里的 URL 剥掉：`text = re.sub(r"[a-z]+://\S+", "", text.lower())`，再匹配状态码与短语；
- `5xx` / `server returned 5` 这类笼统信号可以保留，但同样要在剥掉 URL 之后的文本上判断；
- 补离线断言：`detect("http://h/403.mp4: 404 Not Found") == ""`、`_classify_error(..., "http://h/m.429.mp4")` 不含「429」。

### P3-1 实时监听自检用实例级共享状态，多任务并发时互相干扰

**位置**
- `scraper/watcher.py:90-92` — `_probe_hit` / `_probe_dir` / `_probe_waiting` 是**单份**实例状态；
- `scraper/watcher.py:241-246` — 事件回调按 `_probe_dir` 比对后 `set()`；
- `scraper/watcher.py:320-340` — `_probe_once()` 每次覆盖这三个字段。

**触发条件**
两个自动化任务几乎同时启动（各自目录都要自检），或自检等待期间又新建了任务。

**影响**
- 目录其实收不到事件，但别的任务的探针事件把它 `set` 了 → 自检「通过」，实时监听挂着不工作，文件变更永远不触发（直到用户手动重扫）；
- 自检等待中 `_probe_dir` 被后一个任务覆盖 → 自己的事件被丢弃，误判失败并降级成定时轮询。

单元级两种都已确定性复现；端到端因为自检只需几秒、两任务启动总有先后，没能在真实流程里复现，故定 P3。但一旦命中就是「静默不工作」，用户很难发现。

**修复建议**
把探针状态收进局部对象 + 注册表：

```python
with self._lock:
    self._probes[_norm(directory)] = ev = threading.Event()
# _on_event: ev = self._probes.get(_norm(dirname(path))); ev and ev.set()
finally:
    with self._lock: self._probes.pop(_norm(directory), None)
```

同一目录多个任务可共享一次自检，`_probe_waiting` / `_probe_dir` 两个字段直接删掉。

### P3-2 `sticky=false` 时每次 resolve 都把台账洗回 `fresh`

**位置**
- `scraper/links.py:477-498` — `sticky` 为假时跳过所有缓存分支，直接 `_read_strm()` + `link_upsert()`；
- `scraper/state.py:451-466` — `link_upsert()` 的 UPDATE 分支把 `state` 置 `'fresh'`、`last_error=''`（docstring 说「保留失败次数」，`fail_count` 确实没动，但状态和错误被清了）。

**触发条件**
配置 `links.sticky: false`（「每次以 strm 原文为准」），且某条直链上一次请求被判 `invalid`。

**影响**
- 实测：`state='invalid'`、`fail_count=1` 的记录，再 `resolve()` 一次就变 `fresh`、`last_error` 清空 → `/api/links` 的「失效」永远接近 0，用户看不到哪些链接真的废了；
- 每次 resolve 都写一次库：全量 10k 文件就是 1 万次 UPDATE（虽在同一事务批次内，但纯属浪费）；
- 附带一个文档缺口：`sticky=false` 下 `_maybe_refresh()` 永不执行，刷新钩子完全失效 —— 这点 `docs/115-links.md` 没写。

**修复建议**
- `sticky=false` 时不要 `upsert`，改为在 `signature` 变化时调 `link_touch(key, url, signature, host)`，只更新地址与签名、**保留 state / last_error**；
- 文档补一句「`sticky=false` 时台账只作统计，刷新钩子不参与」。

### P4-1 `_stop_watch` 两个分支完全相同

**位置** `scraper/watcher.py:224-228`

```python
if state and not handles:
    state["active"] = False
elif state:
    state["active"] = False
```

**影响** 无功能影响，纯冗余；`not handles` 原本想表达的「根本没建立监听」这层语义丢了。

**修复** 合并为 `if state: state["active"] = False`；若要区分，就在 `reason` 里区分「未建立监听」与「已停止」。

**位置** `scraper/links.py:131-151`：`per_host_inflight` 与 `max_inflight` 各自夹到 1–64，不保证 `per_host ≤ max`。

## 6. 已确认无问题的重点项

这些是高风险区，本轮专门验过，可以放心：

- 路径越界防护：`/api/files/*` 的 `_within_roots()` 对 `../../etc/passwd` 返回 400（路径不合法）、对 `/etc/passwd`、`C:\Windows\win.ini`、`/root/../etc/passwd` 返回 403（不在媒体库内），无逃逸；
- 任务不丢：暂停 / 取消后 in-flight 项 `reset_one()` 退回 pending，`LinkDeferred` 不计 attempts，进程重启后 `running` 会被复位；
- 状态库并发：单连接 + 锁 + 批量写入，压测下无 `database is locked`；
- 产物复用：三个入队点 + 单条执行对「产物齐全」的判断一致（41 项断言）；
- 图片规格：海报 / 缩略图 / fanart 尺寸与 JPEG 质量符合 Emby/Jellyfin 要求（21 项）；
- 前端：UI 巡检无控制台报错，长文件名不撑破列宽，明暗主题无闪白，选帧弹窗在 6×4 组合下无溢出；
- 鉴权：在 `:6702`（`auth.enabled=true`）上验证，未登录访问 `/api/*` 会被拦截、页面 303 跳登录页，改密后旧会话立即失效；

## 8. 未覆盖与遗留风险

1. **真实 115 网盘未接**：用本地慢源 + 假直链替代，签名过期的真实节奏、风控的触发阈值、`refresh_url` 钩子的真实返回格式都只做了 mock 验证。

5. **跳过项**：`dirview`、`lib_switch`、`poster_status`、`list_images` 因夹具前提不满足未跑，需要时补夹具再验。

### 10.2 过程中另外发现的一个问题

修 P2-4 时实测仍不锁定：换 XFF 十次全部 401。追下去发现 **uvicorn 默认 `proxy_headers=True` 且信任 `127.0.0.1`**，它会自己把 `X-Forwarded-For` 应用到 `request.client.host`，于是应用层的 `trust_proxy=false` 形同虚设。`main.py` 已改成按配置传参：

```python
uvicorn.Config(..., proxy_headers=trust_proxy,
               forwarded_allow_ips="*" if trust_proxy else "")
```

启动日志会打印当前口径（「未信任反向代理：登录限流按 TCP 来源 IP 计」），部署时一眼能确认。

### 10.3 行为变化（升级须知）

1. **`links.sticky=false` 的语义被真正实现了**：以前它也会返回台账缓存，现在是「每次以 strm 原文为准，台账只做统计」。配了这个值的实例会看到每次抓帧多读一次 strm 小文件，且**失败后不再自动走刷新钩子**（`_maybe_refresh` 只在 `sticky=true` 下调用）。写在 `docs/115-links.md` §2.1。
2. **新增 `web.auth.trust_proxy: false`**：挂在反代后面不打开的话，全站共用一个来源 IP，一个人输错密码会锁住所有人。`docs/DEPLOY.md` 加了对应条目，`config.example.yaml` 补了带注释的默认值。
3. **`links.batch_size` 的生效时机**：每轮任务开始时读取一次，跑动中改不会中途缩放并发（`docs/115-links.md` §2.3）。
4. **手动刷新不再「顺手」标记失效**：没配钩子时 `/api/links/refresh` 只重读 strm，内容没变就什么都不做。
